### Added

- **AVIF Item Property Container (`ipco` / `iprp`) round (BUILD_PLAN §7, 1 new Kotlin module + 1 new builder class + 19 new JUnit tests)** — pure-data formatter for the AVIF / HEIF Item Properties parent box (`iprp`) and its mandatory child Item Property Container (`ipco`) per ISO/IEC 14496-12 §8.11.14. Both boxes are plain (non-FullBox) ISOBMFF envelopes, so this round reuses the `IsobmffBox.encodeBox` / `concatPayloads` primitives from Round 22 to compose the `ipco` payload (an ordered concatenation of property child boxes from Rounds 17-20 — `colr`, `mdcv`, `clli`, `pasp`, `clap`, `irot`, `imir`, `pixi`) and the `iprp` payload (one `ipco` followed by 1+ `ipma` boxes from Round 23). Closes the host-side half of BUILD_PLAN §7 "AVIF / HEVC item property container":
  - `IsobmffItemProperties.encodeIpcoBox(properties: List<ByteArray>): ByteArray` — encodes the `ipco` container box: an ordered concatenation of pre-encoded property child boxes wrapped in the canonical 8-byte ISOBMFF header. Each entry must already include its own 8-byte (or 16-byte large-size) header — the typical call site is `IsobmffBox.encodeBox(type, payload)` for plain property boxes (`colr`, `pasp`, `clap`, etc.) or `IsobmffBox.encodeFullBox(type, version, flags, payload)` for FullBox property boxes. Property order matters per ISO/IEC 14496-12 §8.11.14.3 (`ipma` references properties by their 1-based position in this list), which is why this layer preserves caller-supplied order.
  - `IsobmffItemProperties.encodeIprpBox(ipcoBox: ByteArray, ipmaBoxes: List<ByteArray>): ByteArray` — encodes the `iprp` parent box: exactly one `ipco` (mandatory per spec) followed by 1+ `ipma` boxes. Both arguments must already be pre-encoded box byte buffers; typical call sites are [`IsobmffItemProperties.encodeIpcoBox`] for the `ipco` argument and [`ItemPropertyAssociation.encodeBox`] for each `ipma` argument. Throws `IllegalArgumentException` when `ipmaBoxes` is empty.
  - `IsobmffItemProperties.Builder` — order-preserving builder for the `ipco` payload. Each call to `add(encodedBox)` returns the **1-based** property index per §8.11.14.3 — so the caller can pipeline `val colrIdx = builder.add(...)` straight into `ItemPropertyAssociation.Association(propertyIndex = colrIdx, ...)` without manually counting children. `add` defensively copies the input so a caller mutating the source buffer afterward cannot corrupt the eventual `ipco` payload. `build()` returns the complete `ipco` box; equivalent to `encodeIpcoBox(properties)` where `properties` is the list passed to `add` in order. `size()` returns the running property count.
  - **Pinned constants**: `IPCO_BOX_TYPE = "ipco"`, `IPRP_BOX_TYPE = "iprp"`, `MIN_ENCODED_BOX_SIZE = 8` (the canonical ISOBMFF plain-box header size; rejects malformed children at build time), `SCHEMA_VERSION = 1`.
  - **Tests shipped**: `IsobmffItemPropertiesTest` (19 tests covering: `IPCO_BOX_TYPE` / `IPRP_BOX_TYPE` / `SCHEMA_VERSION` / `MIN_ENCODED_BOX_SIZE` constant pins; `encodeIpcoBox` produces 8-byte header-only box for empty properties + documented byte layout for single `colr` property — `8-byte ipco header + 19-byte colr child = 27 bytes`; `encodeIpcoBox` preserves property order (output differs when `pasp` and `irot` are swapped); `encodeIpcoBox` rejects properties shorter than 8 bytes + accepts exactly-8-byte header-only boxes; `encodeIprpBox` produces documented `iprp + ipco + ipma` layout for canonical AVIF still; `encodeIprpBox` concatenates multiple `ipma` boxes after `ipco` in stable order; `encodeIprpBox` rejects empty `ipmaBoxes` per §8.11.14, rejects too-short `ipco` and too-short `ipma`; `Builder.add` returns 1-based indices in append order (`colrIdx=1, pixiIdx=2, irotIdx=3`); `Builder.size()` returns 0 before any `add`; `Builder.add` rejects too-short boxes; `Builder` defensively copies (mutating the source buffer after `add` does not affect the built `ipco`); `Builder.build` matches `encodeIpcoBox` of the same properties; **end-to-end canonical AVIF still test** that builds the `ipco` Builder for `colr`+`pixi`+`pasp`, calls `ItemPropertyAssociation.encodeBox` with the indices, wraps in `iprp`, and decodes the `ipma` payload back to verify the property indices round-trip cleanly with `[colrIdx, pixiIdx, paspIdx]` and the right essential bits `[true, true, false]`).

- **AVIF Item Property Association (`ipma`) round (BUILD_PLAN §7, 1 new Kotlin module + 2 new public data classes + 40 new JUnit tests)** — pure-data formatter for the `ipma` FullBox per ISO/IEC 23008-12 §9.3.2 / ISO/IEC 14496-12 §8.11.14, the linkage layer that maps each item in a HEIF / AVIF file to the list of property indices in `ipco` that apply to that item. Without `ipma`, every property box from Rounds 17-20 (`colr`, `mdcv`, `clli`, `pasp`, `clap`, `irot`, `imir`, `pixi`) lands in the file but no decoder associates them with any image item — `ipma` is the bridge between the property catalog (`ipco`) and the actual items. Closes the host-side half of BUILD_PLAN §7 "AVIF / HEVC item property association table":
  - `ItemPropertyAssociation.Association(propertyIndex: Int, essential: Boolean)` — pure-data carrier for a single `(essential, propertyIndex)` pair. `propertyIndex` is **1-based** per spec — index `0` is reserved to mean "no property" and would silently corrupt the bitstream; `init` rejects `< 1` and `> MAX_LARGE_PROPERTY_INDEX (32767)`. `essential` per ISO/IEC 14496-12 §8.11.14.3: when set, the property is required for correct rendering and a decoder that cannot understand it MUST refuse to display the item — so mandatory metadata like `colr` and `pixi` should be `essential = true`; optional / informational metadata like `irot` / `imir` is `essential = false` per AVIF spec §6.5.10 / §6.5.12.
  - `ItemPropertyAssociation.Entry(itemId: Long, associations: List<Association>)` — one `(itemId, [associations...])` row of the `ipma` table. `itemId` corresponds to a `iloc` / `iinf` item ID elsewhere in the `meta` box; an AVIF still typically has two items (the primary image item plus its `Exif` metadata item). `init` validates `0 <= itemId <= MAX_LARGE_ITEM_ID (4_294_967_295)`, `associations.isNotEmpty()` (an item with zero properties does not need an `ipma` entry), and `associations.size <= MAX_ASSOCIATION_COUNT (255)` — the spec stores it in a single byte.
  - `ItemPropertyAssociation.chooseVersionAndFlags(entries)` — picks the minimum `(version, flags)` combination that can encode every entry. `version = 0` is selected if every itemId fits in 16 bits; otherwise `version = 1`. `flags = 0` is selected if every property index fits in 7 bits; otherwise `flags = FLAG_LARGE_PROPERTY_INDEX`. For an AVIF still with `<=` 65535 items and `<=` 127 properties in `ipco`, this returns `(0, 0)` — the most compact form per HEIF best practice (saves 2 bytes per entry on item-ID width and 1 byte per association on property-index width).
  - `ItemPropertyAssociation.encodePayload(entries, version, flags): ByteArray` — emits ONLY the FullBox payload (the bytes after the 4-byte version+flags slot); the caller wraps with `IsobmffBox.encodeFullBox("ipma", version, flags, payload)`. Wire format per §8.11.14: `uint32_be entry_count` + per-entry `(uint16/uint32 itemId, uint8 association_count, association_count × (1-byte 7-bit-index or 2-byte 15-bit-index packed with the essential bit in the MSB))`. Validates that every itemId / propertyIndex fits the chosen encoding and throws `IllegalArgumentException` otherwise. `decodePayload(bytes, version, flags)` is the inverse; throws `IllegalArgumentException` on under-4-byte input, truncated `item_ID`, truncated `association_count`, and truncated associations.
  - `ItemPropertyAssociation.encodeBox(entries): ByteArray` — convenience that picks the most compact `(version, flags)` via `chooseVersionAndFlags`, calls `encodePayload`, and wraps with `IsobmffBox.encodeFullBox(BOX_TYPE = "ipma", version, flags, payload)` so the muxer gets a complete, ready-to-write `ipma` box (header + payload) in one call.
  - **Pinned constants**: `BOX_TYPE = "ipma"`, `SCHEMA_VERSION = 1`, `FLAG_LARGE_PROPERTY_INDEX = 0x000001`, `MAX_SMALL_PROPERTY_INDEX = 0x7F` (127), `MAX_LARGE_PROPERTY_INDEX = 0x7FFF` (32767), `MAX_SMALL_ITEM_ID = 0xFFFF` (65535), `MAX_LARGE_ITEM_ID = 0xFFFFFFFF`, `MAX_ASSOCIATION_COUNT = 0xFF` (255).
  - **Tests shipped**: `ItemPropertyAssociationTest` (40 tests covering: `BOX_TYPE` and constant pins; `Association` propertyIndex bounds (`< 1`, `> MAX_LARGE_PROPERTY_INDEX`, boundary 1, boundary 32767); `Entry` itemId bounds (`< 0`, `> MAX_LARGE_ITEM_ID`, empty associations, > 255 associations, boundaries 0 and `MAX_LARGE_ITEM_ID`); `chooseVersionAndFlags` returns `(0, 0)` for canonical AVIF still, `(1, 0)` for itemId > 65535, `(0, 1)` for propertyIndex > 127, `(1, 1)` for both, `(0, 0)` for empty entries; byte-layout pins for `entry_count = 0`, single essential prop=1 (`0x81`), single non-essential prop=1 (`0x01`), max small prop=127 essential (`0xFF`), 3-association canonical AVIF still (`0x81 0x82 0x03`), v=1 4-byte itemId big-endian (`0x12345678`), v=0 f=1 2-byte association big-endian (`0x80 0xC8`); `encodePayload` rejects invalid version, out-of-range flags, itemId overflow, propertyIndex overflow; encode → decode round-trip for canonical AVIF still, v=1 large itemId, f=1 large property index (incl. boundary `MAX_LARGE_PROPERTY_INDEX` essential and non-essential), multiple-entries case; `decodePayload` throws on under-4-byte input + truncated item_ID + truncated association_count + truncated association; `encodeBox` produces 20-byte FullBox envelope for canonical AVIF still with `(size=20, type='ipma', version=0, flags=0, payload=8 bytes)`, auto-promotes version=1 when itemId > 65535, auto-promotes flags=1 when propertyIndex > 127; `Entry` and `Association` equality is by content not reference).
  - **58 JUnit suites · 741 tests · 0 failures · 0 errors · 0 skipped** (up from 57 / 701). 40 new tests in `ItemPropertyAssociationTest`. APK 33405 KB (+11 KB).
  - **AVIF muxer status**: with this round, the engine has every host-side primitive needed to mux a fully-tagged AVIF still — every payload from Rounds 17-20 (`colr`, `mdcv`, `clli`, `pasp`, `clap`, `irot`, `imir`, `pixi`) + the canonical box-envelope writer from Round 22 + the item-property association table from Round 23. The remaining work is the actual orchestration (`MetaBox.kt` for the `meta` FullBox + `IpcoBox.kt` for the `ipco` container + `IprpBox.kt` for the `iprp` parent), which can land any time after Phase 1's image encoder ships.

- **ISOBMFF box envelope writer round (BUILD_PLAN §7, 1 new Kotlin module + 23 new JUnit tests)** — the foundational layer that finally lets the engine *mux* the AVIF metadata payloads built in Rounds 17-20 (`colr`, `mdcv`, `clli`, `pasp`, `clap`, `irot`, `imir`, `pixi`) into a real ISOBMFF bitstream. Until this round, every payload formatter shipped *just* the inner bytes (the spec's "BoxBody"); `IsobmffBox` now wraps any payload in a canonical ISO/IEC 14496-12 §4.2 box envelope so the muxer can stop hand-rolling box headers. Closes the host-side half of BUILD_PLAN §7 "AVIF / HEVC / JXL bitstream container — pure-data box envelope writer":
  - `IsobmffBox.kt` — pure-data `object` exposing four formatters and one composer. `boxType(type: String): ByteArray` validates the 4-character ASCII restriction (rejects empty / wrong-length / non-ASCII / non-printable types with `IllegalArgumentException` so a typo never lands silently in the bitstream). `writeBox(out, type, payload)` and `encodeBox(type, payload): ByteArray` produce the canonical `(uint32_be size, uint32_be type, payload)` envelope; when the total `8 + payload.size` exceeds `0xFFFFFFFFL`, the writer automatically promotes to the spec's `large_size` escape form (`size=1, type, uint64_be largesize, payload`) per §4.2.2 BoxHeader. `writeFullBox(out, type, version, flags, payload)` and `encodeFullBox(type, version, flags, payload): ByteArray` produce the `FullBox` flavor (`size, type, uint8 version, uint24_be flags, payload`); `version` validated to `[0, 255]` and `flags` to `[0, 0xFFFFFF]`. `concatPayloads(payloads)` is a tiny helper that flattens a list of child boxes into a single byte buffer the muxer can hand to `encodeBox` for a parent container box (e.g. `meta`, `iprp`, `ipco`). Pinned constants: `SCHEMA_VERSION = 1`, `PLAIN_HEADER_SIZE = 8`, `LARGE_HEADER_SIZE = 16`, `FULLBOX_VERSION_FLAGS_SIZE = 4`, `LARGE_SIZE_THRESHOLD = 0xFFFFFFFFL`. The encoder defensively copies the payload before writing (so the muxer can mutate the source buffer afterward without corrupting the encoded box) AND defensively copies on decode read paths.
  - **Tests shipped**: `IsobmffBoxTest` (23 tests covering: `boxType` accepts canonical 4-char ASCII like `"ftyp"` / `"colr"` / `"meta"`, rejects empty / 3-char / 5-char / non-ASCII / non-printable types; `encodeBox("colr", emptyPayload)` produces 8 bytes (`0 0 0 8 c o l r`); `encodeBox` integrates cleanly with `AvifColrPayload.encodeNclxPayload(WorkingSpace.SRGB.cicp)` to produce the documented 19-byte `colr` envelope (`0 0 0 19 c o l r ` + 11-byte sRGB CICP); `writeBox` and `encodeBox` produce identical output; `encodeFullBox("ipma", version=0, flags=0, payload)` produces the documented `(size, type, 00 00 00 00, payload)` shape; `version=255` and `flags=0xFFFFFF` encode exactly; `version=-1` / `version=256` / `flags=-1` / `flags=0x1000000` rejected; `concatPayloads` flattens an empty list to a 0-byte buffer, a single-element list to a copy of the single payload, and a multi-element list (`colr` envelope + `pasp` envelope) into the documented byte sequence; header-size and large-size threshold constants pinned; defensive payload copy verified by mutating the input array after `encodeBox` returns and confirming the encoded buffer is unchanged; schema version pin).

### Added

- **AVIF auxiliary boxes (`irot` / `imir` / `pixi`) round (BUILD_PLAN §7, 1 new Kotlin module + 1 new data class + 2 new enums + 24 new JUnit tests)** — pure-data byte-layout formatters for the three small AVIF auxiliary metadata boxes that complete the AVIF metadata bundle alongside `colr` (Round 17), `mdcv`/`clli` (Round 18), and `pasp`/`clap` (Round 19): image rotation (`irot`, ISO/IEC 23008-12 §6.5.10), image mirror (`imir`, ISO/IEC 23008-12 §6.5.12), and pixel information (`pixi`, ISO/IEC 23008-12 §6.5.6). With these, the engine has every host-side AVIF metadata serializer it needs to mux a fully-tagged AVIF bitstream the moment Phase 1 lands. Closes the host-side half of BUILD_PLAN §7 "AVIF / HEVC sample-aspect + clean-aperture metadata" plus its sibling rotation / mirror / bit-depth tagging:
  - `AvifAuxiliaryBoxes.Rotation` — enum with `Rot0` / `Rot90` / `Rot180` / `Rot270`. Carries both `degrees` (0/90/180/270, clockwise) and `wireValue` (0..3, the spec's `angle / 90` form). `Rotation.fromDegrees(int)` normalizes any input modulo 360 (so `-90` → `Rot270`, `450` → `Rot90`); rejects non-90-multiple inputs. `Rotation.fromWireValue(int)` rejects values outside `[0, 3]`. Used to express sensor orientation (e.g. portrait capture from a landscape-natural sensor) without re-encoding pixels.
  - `AvifAuxiliaryBoxes.MirrorAxis` — enum with `Horizontal` (top-bottom flip, wire value 0) and `Vertical` (left-right flip, wire value 1). Names are spec-aligned per ISO/IEC 23008-12 — the spec's `axis_horizontal` is the vertical flip a layperson would expect, but we keep spec-aligned names so callers reading the spec directly aren't confused. Used for selfie-mode captures from front-facing sensors.
  - `AvifAuxiliaryBoxes.PixiPayload(bitDepths: IntArray)` — data class carrying the per-channel bit depth list. `init` enforces `bitDepths.size in [1, 255]` and every depth in `[1, 255]`. Custom `equals` / `hashCode` compare arrays by content (Kotlin's data class default would compare by reference). Five pre-computed presets: `MONO_8` (1 ch, `8`), `RGB_8` (3 ch, `8/8/8`), `RGBA_8` (4 ch, `8/8/8/8`), `RGB_10` (3 ch, `10/10/10` — HDR10 / Rec.2020 PQ default), `RGB_12` (3 ch, `12/12/12` — libjxl default for high-bit RAW-derived stills).
  - `AvifAuxiliaryBoxes.encodeIrot(rotation)` produces exactly 1 byte (`wireValue` in the low 2 bits); `decodeIrot(bytes)` is the inverse and silently masks off bits 7..2 for tolerance with pre-spec encoders. `encodeImir(axis)` produces exactly 1 byte (`wireValue` in bit 0); `decodeImir(bytes)` masks off bits 7..1. `encodePixi(pixi)` produces `1 + bitDepths.size` bytes (channel count followed by per-channel depths); `decodePixi(bytes)` validates the declared channel count matches the payload length. All three decoders throw `IllegalArgumentException` on wrong byte lengths. Pinned constants: `IROT_PAYLOAD_LENGTH = 1`, `IMIR_PAYLOAD_LENGTH = 1`, `SCHEMA_VERSION = 1`.
  - **Tests shipped**: `AvifAuxiliaryBoxesTest` (24 tests covering: `Rotation` enum degrees + wireValue mapping, `Rotation.fromDegrees` normalizes negative + over-360 angles + rejects non-90-multiple, `Rotation.fromWireValue` rejects out-of-range, `encodeIrot` produces 1 byte with wireValue, `encode → decode` round-trips every rotation, `decodeIrot` tolerates non-zero reserved bits, `decodeIrot` rejects wrong lengths; `MirrorAxis` wire values pinned, `MirrorAxis.fromWireValue` rejects out-of-range, `encodeImir → decodeImir` round-trips both axes, `decodeImir` tolerates non-zero reserved bits + rejects wrong lengths; `PixiPayload` presets cover MONO/RGB/RGBA/10-bit/12-bit, rejects empty / out-of-range bit depths, `equals` and `hashCode` compare arrays by content, `encodePixi` writes `count, depths...`, RGBA-8 produces `[4, 8, 8, 8, 8]`, RGB-10 produces `[3, 10, 10, 10]`, encode→decode round-trips every preset, `decodePixi` rejects empty + truncated + zero-channel + max-255-channel payloads, schema version pin).

  - **AVIF metadata bundle status**: with this round, every spec-required AVIF bitstream-tag box has a pure-data, JVM-tested formatter shipped: `colr` (CICP nclx + ICC prof) from Round 17 + `mdcv` / `clli` (HDR static metadata) from Round 18 + `pasp` / `clap` (pixel aspect + clean aperture) from Round 19 + `irot` / `imir` / `pixi` (rotation + mirror + pixel info) from Round 20. - **ISOBMFF `pasp` + `clap` formatter round (BUILD_PLAN §7, 1 new Kotlin module + 2 new public data classes + 20 new JUnit tests)** — pure-data byte-layout formatters for the two ancillary ISOBMFF "transformative" boxes that ride alongside the `colr` (CICP), `mdcv`, and `clli` boxes in AVIF / HEVC samples: pixel aspect ratio (`pasp`, ISO/IEC 14496-12 §12.1.4.3) and clean aperture (`clap`, ISO/IEC 14496-12 §12.1.4.3). Both boxes are mandatory in libavif's strict mode whenever the engine wants to cleanly express a non-square pixel grid or a content rectangle that isn't aligned to the codec's coded-image rectangle. Closes the host-side half of BUILD_PLAN §7 "AVIF / HEVC sample-aspect + clean-aperture metadata":
  - `IsobmffSampleAspect.PaspPayload(hSpacing, vSpacing)` — data class holding the pixel aspect ratio as the integer ratio `hSpacing : vSpacing`. `init` enforces both fields are `>= 1`. `PaspPayload.SQUARE` (`1:1`) is the pre-computed default for every modern phone / DSLR / mirrorless camera (square-pixel sensors).
  - `IsobmffSampleAspect.ClapPayload(widthN, widthD, heightN, heightD, horizOffN, horizOffD, vertOffN, vertOffD)` — data class holding the clean-aperture rectangle as four rationals (width, height, horizontal offset, vertical offset). Width / height numerators + all four denominators must be `>= 1`; offset numerators are signed (the spec's center-form coordinates can be negative). `ClapPayload.centeredCropOf(codedWidth, codedHeight, cropX, cropY, cropW, cropH)` is a convenience constructor that takes a top-left-anchored pixel rectangle and rephrases it into the spec's center-form (centered at `(codedCenter + offN/offD, ...)`); validates that the requested crop lies entirely within the coded image.
  - `IsobmffSampleAspect.encodePasp(pasp)` produces exactly 8 big-endian bytes (`uint32_be hSpacing` + `uint32_be vSpacing`); `decodePasp(bytes)` is the inverse. `encodeClap(clap)` produces exactly 32 big-endian bytes (`uint32_be widthN/widthD/heightN/heightD` + `int32_be horizOffN` + `uint32_be horizOffD` + `int32_be vertOffN` + `uint32_be vertOffD`); `decodeClap(bytes)` is the inverse. Both decoders throw `IllegalArgumentException` on wrong byte lengths and on `uint32 > Int.MAX_VALUE` overflow (we cap to `[0, 2^31 - 1]` because Kotlin/JVM stores the round-trip values as signed `Int`s). ## Release procedure (reminder)

When tagging a release:

1. Run `.\scripts\pns_verify_toolchain.ps1` (must exit 0).
2. Move all items from **Unreleased** into a new `## <version> - YYYY-MM-DD` section.
3. Annotated git tag, then publish a GitHub Release using `RELEASE_NOTES_TEMPLATE.md`.
4. Add a fresh empty `## Unreleased` section above the new versioned section.
